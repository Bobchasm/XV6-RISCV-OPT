# 调度测试与性能分析

## 1. 设计原则

测试程序不直接访问调度器内部变量，也不把实验逻辑写入 `sched.c`。
RR、静态优先级和 MLFQ 都运行同一个用户态负载，由宿主机脚本统一构建、
启动和解析结果。

因此，新增调度策略时只需要让它能够正常编译、启动，测试模块不需要修改。

当前静态优先级策略约定 `priority` 数值越大表示优先级越高；当多个
可运行进程优先级相同时，再按照轮转顺序选择。现阶段进程优先级仍使用
PCB 初始化时的默认值 `SCHED_DEFAULT_PRIORITY`；现在可以通过
`set_prio` 为测试进程设置不同优先级，并进行不同优先级之间的调度效果
对比。

## 2. 测试负载

`user/schedbench.c` 会创建一组子进程，任务类型按顺序循环：

- `cpu`：执行计算工作单元并跨 tick 记录，模拟 CPU 密集型任务；
- `io`：反复 `pause(1)`，模拟频繁等待的 I/O 型任务；
- `mixed`：计算和等待交替，模拟混合负载。

命令格式：

```text
schedbench [jobs] [work]
```

默认值为 `jobs=6`、`work=40`。为了让 CPU 密集型任务跨越多个 tick，
建议性能对比时使用 `work=40` 或更大值，不要使用过小的工作量。

## 3. 输出指标

用户程序为每个任务输出结构化的一行数据，宿主机脚本转换为 CSV。
当前已有指标如下：

| 中文指标名称 | CSV 字段 | 计算方式或含义 |
|---|---|---|
| 周转时间 | `turnaround` | `finish - start`，任务从开始记录到完成所经过的 xv6 tick 数 |
| 带权周转时间 | `weighted_turnaround` | `turnaround / service`，用于归一化比较不同工作量任务的完成效率 |
| 响应延迟 | `response` | 第一次完成一个工作片段的时间减去任务开始时间 |
| 吞吐量 | `throughput` | 本轮完成任务数除以实验总 tick 数 |
| 服务量近似值 | `service` | 测试程序配置的 `work` 值，表示任务需要完成的工作量 |
| 开始时间 | `start` | 任务开始记录时的 xv6 tick |
| 首次进展时间 | `first` | 任务第一次完成工作片段时的 xv6 tick |
| 完成时间 | `finish` | 任务完成时的 xv6 tick |

其中，`turnaround`、`weighted_turnaround`、`response` 和 `throughput`
就是本实验当前用于比较调度策略的主要性能指标。

当前已经提供 `set_prio`、`get_psinfo` 和 `sys_stat`。其中
`get_psinfo` 可以查询进程的优先级、队列层级、时间片、运行时间、
就绪次数、等待次数和状态统计，`sys_stat` 可以汇总进程数量及全局
调度计数。`service` 仍是用户态配置的工作量，不是内核精确 CPU
运行时间；`response` 仍是用户态近似的响应延迟，不等同于进程第一次
获得 CPU 的精确时间。

这三个系统调用位于公共进程管理层，不调用具体调度策略的选择函数，
因此不依赖 RR、静态优先级或 MLFQ 是否已经实现。`set_prio` 只更新
PCB 中共享的 `priority` 字段，具体策略是否使用该字段由策略自身决定；
`get_psinfo` 和 `sys_stat` 只负责安全地复制调度状态快照。

接口形式如下：

| 系统调用 | 用户态原型 | 作用 |
|---|---|---|
| `set_prio` | `int set_prio(int pid, int priority)` | 修改指定 PID 的优先级，成功返回 `0` |
| `get_psinfo` | `int get_psinfo(int pid, struct psinfo *)` | 查询指定进程快照，失败返回 `-1` |
| `sys_stat` | `int sys_stat(struct sched_stat *)` | 查询全局调度统计，失败返回 `-1` |

当前 `set_prio` 没有额外限制调用者身份，适合课程实验中由测试程序
统一设置子进程优先级；正式系统中可以再增加权限检查。

可以用下面的命令验证接口：

```text
schedinfo [priority]
```

它会先调用 `set_prio` 修改自身优先级，再通过 `get_psinfo` 和
`sys_stat` 输出进程快照与全局统计。

后续 Member 4 增加监控接口后，可以在同一 CSV 中追加
`schedule_count`、`run_time`、`wait_count` 等内核级指标，不需要改变负载模型。

## 4. 运行方式

只在终端显示 CSV：

```bash
python3 scripts/run-schedbench.py --policies SCHED_RR
```

写入结果文件：

```bash
python3 scripts/run-schedbench.py \
  --policies SCHED_RR \
  --jobs 6 \
  --work 40 \
  --output results/rr.csv
```

写文件时，CSV 保存逐任务原始数据；终端仍会打印按策略和任务类型分组的
平均周转时间、平均带权周转时间、平均响应时间和吞吐量汇总。

未来策略实现并注册后，可以一次对比：

```bash
python3 scripts/run-schedbench.py \
  --policies SCHED_RR,SCHED_STATIC_PRIORITY,SCHED_MLFQ \
  --output results/all.csv
```

脚本会为每个策略重新编译内核，并固定使用 `CPUS=1`，减少多核调度带来的
实验噪声。不同策略应使用相同的 `jobs`、`work` 和 CPU 数量。
