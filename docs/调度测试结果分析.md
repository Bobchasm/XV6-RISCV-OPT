# 调度测试结果分析

## 1. 测试范围

测试日期：2026 年 9 月 21 日。

比较对象：

- `RR`：时间片轮转；
- `SPQ`：静态优先级队列；
- `MLFQ`：多级反馈队列。

正式性能对比固定 `CPUS=1`，避免多核调度噪声。三种策略使用相同的任务数、
工作量、优先级和场景参数。结果文件位于 `results/`，图位于
`analysis/plots/`。

本轮生成 14 个 CSV，覆盖：

- `work=10/40/80`，每种策略 3 次重复；
- `compute`、`io`、`mixed` 三类场景，每种策略 3 次重复；
- 单任务 `jobs=1`；
- 高并发 `jobs=12`；
- MLFQ 长任务和 I/O/混合专项；
- SPQ 两组优先级反转实验。

所有最终 CSV 均通过字段、策略覆盖、空值和非负数检查，共 14 个文件，QEMU
测试结束后没有残留进程。

## 2. 指标说明

- `turnaround`：任务从开始到结束的 tick 数；
- `response`：用户任务开始到首次运行的 tick 数；
- `kernel_response`：从进程创建到首次被调度的 tick 数；
- `run_ticks`：统计到的运行 tick；
- `total_ready_time`：就绪等待时间累计值；
- `throughput`：本次实验完成任务数除以实验 elapsed tick；
- `service`：用户程序传入的工作量近似值，不是精确 CPU 时间。

由于 xv6 tick 粒度较粗，短任务的多个指标可能出现大量 0 或相同值。短任务
结果应结合 `work=40/80` 和场景结果一起看，不能把一个 tick 内的差异解释成
精确的纳秒级性能差异。

## 3. 工作量趋势

从 `schedbench-rr-spq-mlfq-work10.csv`、`work40.csv` 和 `work80.csv` 看：

- `work=10` 时三种算法几乎完全重合，任务太短，调度策略差异没有充分展开；
- `work=40` 时三者的平均周转时间仍很接近，SPQ 在 CPU 类任务上略低，
  MLFQ 的运行 tick 和等待统计接近 RR；
- `work=80` 时差异更明显。SPQ 的 CPU 类任务平均周转约为 2.17 tick，
  RR 约为 4.17 tick，MLFQ 约为 3.67 tick；但 SPQ 的
  `kernel_response` 和 `total_ready_time` 波动也更大；
- RR 的行为较稳定，MLFQ 在 CPU 密集工作量增加后会体现更多运行 tick，
  但没有在所有指标上同时优于另外两种策略。

这些结果说明工作量增大后才有足够的抢占和排队行为可观察。当前基准中的
I/O 和混合任务包含大量睡眠，因此其周转时间主要受工作量和睡眠路径影响，
不能只用 CPU share 判断优劣。

## 4. 场景对比

### Compute

`compute` 场景中三种策略的任务很短，平均周转时间接近 0。SPQ 的平均
`run_ticks` 和周转时间略低，MLFQ 有少量任务经历额外 tick。该结果更适合
说明三种实现都能完成计算负载，不足以支持强的性能排序。

### I/O

`io` 场景中 RR 平均周转约 4.72 tick，SPQ 约 4.11 tick，MLFQ 约 4.39 tick。
SPQ 在本组参数下略好，但差异不大；MLFQ 的平均用户响应约 1.61 tick，高于
RR 和 SPQ 的约 1.06 tick。I/O 负载的主要观察点是睡眠/唤醒后的响应和等待，
而不是 CPU 运行 tick。

### Mixed

`mixed` 场景中 SPQ 的平均周转约 1.39 tick，RR 约 1.56 tick，MLFQ 约
1.72 tick。SPQ 的交互任务响应较低，但其运行 tick 和结果会随任务到达顺序
变化。该结果体现了静态优先级对当前优先级配置的影响，不代表 SPQ 在所有
混合负载中都更好。

## 5. 边界和专项结果

- `jobs=1` 主要提供无竞争基线，三种策略差异很小；
- `jobs=12` 能够产生更明显的排队，但仍未发现 QEMU 卡死、内核 panic 或
  任务无法回收；
- MLFQ 长任务专项成功完成，低队列任务没有在本次参数下永久饥饿；
- SPQ 优先级反转实验显示，调整 CPU/I/O 优先级会改变 CPU 类与 I/O 类任务
  的响应和周转，说明优先级参数确实进入了调度行为；
- xv6 用户态回归测试通过，输出为 `ALL TESTS PASSED`。

## 6. 测试过程中的异常和修复

高工作量和场景测试初次运行时曾出现 CSV 记录不完整。原因是多个 xv6 用户进程
使用逐字符 `write` 输出长结果行，串口输出发生交错，解析器收到缺少字段的记录。
随后做了两项修复：

1. 调度结果记录改为用户态拼接完整行后一次写出；
2. 宿主机解析器允许控制台记录跨行，并在缺少必需字段时立即失败。

修复后重新构建并重跑全部测试，最终 14 个 CSV 均完整通过校验。这个限制仍应
记录在实验报告中：当前结果依赖 xv6 模拟串口输出，不应把一次异常的半行数据
当成真实调度性能。

## 7. 关于火焰图

本实验当前没有函数调用栈采样、`perf` 数据或内核函数耗时数据，因此不能生成
严格意义上的 OS 火焰图。现有 CSV 只记录任务级指标，如任务周转、响应、运行
tick、就绪等待和调度次数。

本轮使用折线图、分组柱状图和带误差线柱状图。若后续要做真正火焰图，需要增加
宿主机或 xv6 内核侧的采样机制，记录调用栈、函数符号和采样时间，再用
`火焰图.pl` 或同类工具折叠和绘制。

## 8. 结论

在本轮 `CPUS=1`、6 个任务、给定优先级和工作量下：

- RR 提供了较稳定、容易解释的基线；
- SPQ 对当前优先级配置下的 CPU 和混合任务有一定优势，但等待和首次调度
  指标更依赖优先级与任务顺序；
- MLFQ 能够完成长任务和睡眠/唤醒路径，表现介于另外两者之间，不能概括为
  所有指标最优；
- 结论应限定在当前 xv6 实现、tick 粒度和测试负载，不应外推到通用操作系统
  或所有优先级配置。

报告插图建议使用 `analysis/plots/` 中的工作量趋势图、场景周转/响应图和
`work40_variability` 误差线图。
